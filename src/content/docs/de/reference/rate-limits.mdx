## Wie Rate-Limits funktionieren

- **TPM (Token pro Minute)** — Best-Effort-*Obergrenze* für verarbeitete Eingabe-Token pro Minute; kein SLA-gestützter Durchsatzwert
- **RPM (Anfragen pro Minute)** — Best-Effort-*Obergrenze* für API-Anfragen pro Minute; kein SLA-gestützter Anfragerate-Wert
- Limits gelten je Projekt — alle in einem Projekt erzeugten API-Schlüssel teilen sich das Kontingent
- Sowohl Eingabe- als auch Ausgabe-Token zählen zu den TPM-Limits

Anders gesagt: RPM/TPM zeigen, ab wann die Plattform Ihren Traffic *drosselt*. Sie sagen **nichts** darüber aus, mit welcher Rate die Plattform Ihren Traffic *bedient*. Im Shared Service hängt die tatsächlich erreichte Rate von der Plattformlast und der Nutzung desselben Modells durch andere Tenants ab.

### Wie das Minutenfenster gezählt wird

Die „Minute" in RPM und TPM ist eine **Kalenderminute**, kein gleitendes 60-Sekunden-Fenster. Jeder Zähler läuft von `hh:mm:00` bis `hh:mm:59` UTC und wird zu Beginn der nächsten Minute auf null zurückgesetzt. Die Zähler werden je Projekt und je Modell geführt: Alle API-Schlüssel desselben Projekts teilen sich einen Satz Zähler pro Modell.

- **RPM** wird bei Annahme der Anfrage um eins erhöht.
- **Eingabe-TPM** wird bei Annahme der Anfrage belastet, auf Basis einer Schätzung aus dem Anfragetext. Eine Schätzung ist nötig, weil die Anfrage angenommen werden muss, bevor ein Modell läuft. Sie kann daher in beide Richtungen von den `prompt_tokens` abweichen, die das Modell später in `usage` meldet. Planen Sie etwas Spielraum unter dem Limit ein, statt mit dem exakten Wert zu rechnen. Sobald die Antwort vorliegt, werden gecachte Prompt-Token mit 75 % Rabatt dem Fenster gutgeschrieben. Sie zählen also nur zu einem Viertel gegen das Limit: 100 gecachte Token verbrauchen 25 Token Ihres Eingabe-TPM.
- **Ausgabe-TPM** wird mit den Completion-Token belastet, die das Modell nach Abschluss der Antwort meldet.

Die Schätzung wird nur für das Rate Limiting verwendet. Die Abrechnung basiert immer auf den exakten Token-Zahlen, die das Modell in `usage` meldet.

Da das Fenster an der Uhr ausgerichtet ist, werden die Zähler zu Beginn jeder Minute zurückgesetzt, nicht 60 Sekunden nach Ihrer letzten Anfrage. Eine Anfrage um `12:00:59` und eine um `12:01:00` fallen in verschiedene Fenster.

Manche `429`-Antworten haben diese Ursache: Anfragen, die ein clientseitiger Timer im Abstand von 60 Sekunden sendet, können auf dem Gateway dennoch in dieselbe Kalenderminute fallen. Der `429`-Body nennt die verbleibenden Sekunden im aktuellen Fenster.


## Rate-Limit-Antwort-Header

Antworten von Azure-gehosteten GPT-Modellen enthalten Header, mit denen Sie die Nutzung gegen die Limits verfolgen:

:::note
Rate-Limit-Header werden derzeit von Azure-gehosteten Modellen zurückgegeben. Open-Source-Modelle auf T-Cloud (zum Beispiel `gpt-oss-120b`) geben diese Header nicht zurück.

| Header | Beschreibung |
|---|---|
| `x-ratelimit-limit-requests` | Maximale erlaubte Anfragen pro Minute |
| `x-ratelimit-limit-tokens` | Maximale erlaubte Token pro Minute |
| `x-ratelimit-remaining-requests` | Verbleibende Anfragen im aktuellen Zeitfenster |
| `x-ratelimit-remaining-tokens` | Verbleibende Token im aktuellen Zeitfenster |
| `x-ratelimit-reset-requests` | Zeit bis zum Zurücksetzen des Anfrage-Limits |
| `x-ratelimit-reset-tokens` | Zeit bis zum Zurücksetzen des Token-Limits |

## Umgang mit Rate-Limits

Wenn Sie ein Rate-Limit überschreiten, gibt die API einen `429 Too Many Requests`-Fehler zurück. Best Practices:

1. **Antwort-Header überwachen** — Prüfen Sie die `x-ratelimit-remaining-*`-Header, um Limits nicht zu erreichen
2. **Exponentielles Backoff implementieren** — Verlängern Sie die Wartezeit zwischen Wiederholungsversuchen
3. **Anfragen bündeln** — Fassen Sie mehrere kleine Anfragen zu weniger größeren zusammen
4. **Antworten cachen** — Vermeiden Sie das Wiederholen identischer Anfragen
5. **Queue-API verwenden** — Für Batch-Workloads warten [`/queue`-Endpunkte](/de/guides/queued-requests) bis zu zwei Minuten auf Ihr Limit, statt sofort `429` zurückzugeben

```python
import time

from openai import OpenAI, RateLimitError

client = OpenAI()

def safe_completion(messages, max_retries=3):
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(
                model="gpt-oss-120b",
                messages=messages,
            )
        except RateLimitError:
            wait_time = 2 ** attempt
            print(f"Rate limited. Waiting {wait_time}s...")
            time.sleep(wait_time)
    raise Exception("Max retries exceeded")
```

## Servicehinweis zu den veröffentlichten RPM- und TPM-Werten

<sup>&ast;</sup> Die auf dieser Seite gezeigten Werte für Anfragen pro Minute (RPM) und Token pro Minute (TPM) sind **Best-Effort-/Best-Case-Obergrenzen** im Shared LLM Serving Service. Sie geben den vertraglich maximal zulässigen Verbrauch an — keinen zugesicherten Durchsatz. Es gelten die folgenden Bedingungen:

- **Nicht Teil des [Service Level Agreements (SLA)](/de/reference/service-levels).** Das 99,5%-Verfügbarkeits-SLA deckt ausschließlich die Erreichbarkeit der API ab; es erstreckt sich nicht auf RPM, TPM, Durchsatz, End-to-End-Latenz oder Time-to-First-Token.
- **Für Open-Source-Modelle auf T-Cloud** kann der tatsächlich erreichte Durchsatz bei hoher gleichzeitiger Nachfrage deutlich unterhalb der veröffentlichten Obergrenzen liegen. End-to-End-Latenz und Time-to-First-Token variieren ebenfalls mit der Plattformlast.
- **Der Wert "Embedding-Modelle (RPM)"** in der Tabelle "Limits nach Tarif" ist die Anzahl der Anfragen pro Minute für die Embedding-Modelle; präzise Limits variieren je Modell. Professional und Agentic umfassen Premium-Modelle (z. B. Claude Opus) zusätzlich zum Standard-Katalog des Essential-Tarifs.
- **Für vertragliche Zusagen zu Durchsatz, End-to-End-Latenz oder Time-to-First-Token** siehe [Dedicated LLM Serving](/de/plans/dedicated) — dort können solche Zusagen als Performance-SLAs auf reservierter Hardware verhandelt werden.


## Höhere Limits benötigt?

- **Tarif upgraden** — Höhere Stufen haben deutlich höhere TPM- und RPM-Limits
- **Auf Dedicated LLM Serving wechseln** — Im [Dedicated LLM Serving](/de/plans/dedicated) gibt es keine RPM/TPM-Obergrenzen. Sie reservieren GPU-Hardware und verbrauchen so viele Token, wie diese erzeugen kann — sinnvoll für bursty Traffic oder strikte Latenz-SLAs, die der Shared Service nicht garantieren kann
