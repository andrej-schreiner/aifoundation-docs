## How Rate Limits Work

- **TPM (Tokens per Minute)** — best-effort *ceiling* on input tokens processed per minute; not an SLA-backed throughput target
- **RPM (Requests per Minute)** — best-effort *ceiling* on API requests per minute; not an SLA-backed request-rate target
- Limits apply at the project level — all API keys you generate in a project share the same quota
- Both input and output tokens count toward TPM limits

In other words, RPM/TPM tell you when the platform will start *throttling* your traffic. They do **not** tell you the rate at which the platform will *serve* your traffic. On the shared service, the realized rate depends on platform load and other tenants' usage of the same model.

### How the minute window is counted

The "minute" in RPM and TPM is a **calendar minute**, not a sliding 60-second window. Every counter runs from `hh:mm:00` to `hh:mm:59` UTC and resets to zero at the start of the next minute. Counters are kept per project and per model: all API keys in the same project share one set of counters for a model.

- **RPM** is charged by one for each request when it is admitted.
- **Input TPM** is charged when the request is admitted, using an estimate made from the request text. An estimate is used because the request must be admitted before any model runs, so it can differ from the `prompt_tokens` the model later reports in `usage`, in either direction. Keep some margin below the limit rather than planning on the exact figure. Once the response is known, cached prompt tokens are refunded to the window at a 75% discount. For example, 100 cached tokens use 25 tokens of your input TPM.
- **Output TPM** is charged with the completion tokens the model reports when the response completes.

The estimate is used for rate limiting only. Billing always uses the exact token counts the model reports in `usage`.

Because the window is aligned to the clock, the counters reset at the top of each minute, not 60 seconds after your last request. A request at `12:00:59` and one at `12:01:00` fall into different windows.

Some `429` responses are caused by this: requests spaced 60 seconds apart by a client-side timer can still fall into the same calendar minute on the gateway. The `429` body states the seconds left in the current window.


## Rate Limit Response Headers

Responses from Azure-hosted GPT models include headers that help you track usage against limits:

:::note
Rate limit headers are currently returned by Azure-hosted models. Open-source models hosted on T-Cloud (for example `gpt-oss-120b`) do not return these headers.

<div set:html="<!-- TODO(andrej): the published examples of these headers used gpt-5 and gpt-5-mini. Confirm the same headers on gpt-6.1-sol, which this sample now calls. -->"></div>
:::

| Header | Description |
|---|---|
| `x-ratelimit-limit-requests` | Maximum requests allowed per minute |
| `x-ratelimit-limit-tokens` | Maximum tokens allowed per minute |
| `x-ratelimit-remaining-requests` | Requests remaining in the current window |
| `x-ratelimit-remaining-tokens` | Tokens remaining in the current window |
| `x-ratelimit-reset-requests` | Time until the request limit resets |
| `x-ratelimit-reset-tokens` | Time until the token limit resets |

## Handling Rate Limits

When you exceed a rate limit, the API returns a `429 Too Many Requests` error. Best practices:

1. **Monitor response headers** — Check `x-ratelimit-remaining-*` headers to avoid hitting limits
2. **Implement exponential backoff** — Wait longer between retries
3. **Batch requests** — Combine multiple small requests into fewer larger ones
4. **Cache responses** — Avoid repeating identical requests
5. **Use the Queue API** — For batch workloads, [`/queue` endpoints](/guides/queued-requests) wait up to two minutes for your limit instead of returning `429` right away

```python
import time

from openai import OpenAI, RateLimitError

client = OpenAI()

def safe_completion(messages, max_retries=3):
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(
                model="gpt-oss-120b",
                messages=messages,
            )
        except RateLimitError:
            wait_time = 2 ** attempt
            print(f"Rate limited. Waiting {wait_time}s...")
            time.sleep(wait_time)
    raise Exception("Max retries exceeded")
```

## Service note on the published RPM and TPM values

<sup>&ast;</sup> The Requests-per-Minute (RPM) and Tokens-per-Minute (TPM) figures throughout this page are **best-effort, best-case ceilings** for the Shared LLM Serving Service. They denote the maximum traffic permitted under the contract — not a guaranteed level of throughput. The following conditions apply:

- **Not part of the [Service Level Agreement (SLA)](/reference/service-levels).** The 99.5% availability SLA covers API reachability only; it does not extend to RPM, TPM, throughput, end-to-end latency, or time-to-first-token.
- **For open-source models hosted on T-Cloud**, realised throughput may fall substantially below the published ceilings during periods of peak concurrent demand. End-to-end latency and time-to-first-token also vary with platform load.
- **The "Representative RPM" figure** in the Limits-by-Plan table is an illustrative value for a representative T-Cloud model; precise limits vary by model. Professional and Agentic include Premium-tier models (e.g. Claude Opus) in addition to the Standard catalogue available on Essential.
- **For contractual guarantees on throughput, end-to-end latency, or time-to-first-token**, see [Dedicated LLM Serving](/plans/dedicated), where such commitments can be negotiated as performance SLAs on reserved hardware.
